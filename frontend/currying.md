# Каррирование и частичное применение

<details>
<summary><b>Что такое каррирование? (Циан)</b></summary>

**Каррирование (currying)** — трансформация функции от многих аргументов в цепочку функций от одного аргумента: `f(a, b, c)` превращается в `f(a)(b)(c)`.

Функция при этом не вызывается, пока не получит все нужные аргументы. Промежуточные вызовы просто копят переданное в замыкании и возвращают новую функцию.

Зачем это нужно на практике:

- **Конфигурируемые функции.** Один раз фиксируем «настройку», дальше пользуемся коротким вызовом: `const logError = log('ERROR')`.

- **Переиспользование в `map`/`filter`.** Эти методы ждут функцию от одного аргумента, и каррированная функция подходит без обёртки-стрелки: `users.map(pick('name'))`.

- **Композиция.** `compose` и `pipe` работают с унарными функциями, поэтому каррирование — предусловие для функционального стиля.

```js
const log = (level) => (message) => console.log(`[${level}] ${message}`);

const error = log('ERROR');
error('Не удалось загрузить профиль'); // [ERROR] Не удалось загрузить профиль
```

---

### Ответ для лунтиков

Представьте кофемашину с тремя ручками: тип напитка, размер стакана, количество сахара. Обычная функция — это машина, которая не начнёт варить, пока вы не выставите все три ручки разом.

Каррированная версия — это машина, которая запоминает каждую ручку по отдельности. Выставили «капучино» — машина ещё не варит, но теперь это «машина для капучино». Выставили «большой» — теперь это «машина для большого капучино». И только когда вы выставите последнюю ручку, она начнёт варить.

Удобство в том, что «машину для большого капучино» можно поставить на кухне и дальше нажимать одну кнопку, а не выставлять три ручки каждое утро.

<summary><b>Чем каррирование отличается от частичного применения? (Циан)</b></summary>

Это разные вещи, которые часто путают. **Частичное применение (partial application)** — фиксация части аргументов с получением функции меньшей арности. **Каррирование** — превращение функции в цепочку строго унарных вызовов.

| | Каррирование | Частичное применение |
| --- | --- | --- |
| Результат | цепочка функций от одного аргумента | одна функция от оставшихся аргументов |
| Сколько шагов | столько, сколько аргументов | ровно один |
| `f(a, b, c)` даёт | `f(a)(b)(c)` | `g(b, c)` с зафиксированным `a` |

Частичное применение проще всего сделать через `bind`:

```js
function mul(a, b) {
  return a * b;
}

const double = mul.bind(null, 2); // фиксируем первый аргумент
double(5); // 10
```

На практике границу размывают: большинство библиотечных реализаций `curry` (например, в lodash) принимают аргументы и по одному, и пачками — то есть используют частичное применение как механику внутри каррирования.

<details>
<summary><b>Как реализовать универсальную функцию curry? (Циан)</b></summary>

Идея: копим аргументы в замыкании, пока их не наберётся столько же, сколько объявлено у исходной функции. Как только набрали — вызываем.

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }

    return function (...rest) {
      return curried.apply(this, [...args, ...rest]);
    };
  };
}

const sum3 = (a, b, c) => a + b + c;
const csum = curry(sum3);

csum(1)(2)(3);  // 6
csum(1, 2)(3);  // 6
csum(1)(2, 3);  // 6
csum(1, 2, 3);  // 6
```

Что стоит проговорить, если просят написать это на интервью:

- `fn.length` — **арность** функции, количество объявленных параметров.

- `apply(this, ...)` нужен, чтобы не потерять контекст, если каррированную функцию вызывают как метод объекта.

- Аргументы копятся именно в замыкании — каждый промежуточный вызов создаёт новую область видимости и не мутирует общую.

**Подводный камень с `fn.length`.** Rest-параметры и параметры со значением по умолчанию в арность не попадают, поэтому такую функцию каррировать не выйдет — она вызовется слишком рано:

```js
const bad = (a, b = 1, c) => a + b + c;
bad.length; // 1, а не 3
```

Из-за этого библиотечные реализации разрешают задавать арность явно вторым аргументом.

Та же логика в одну строку на стрелках:

```js
const curry = (fn) => {
  const curried = (...args) =>
    args.length >= fn.length ? fn(...args) : (...rest) => curried(...args, ...rest);

  return curried;
};
```

Стрелочный вариант короче, но теряет `this` — для методов объекта он не подойдёт.

<details>
<summary><b>Как реализовать бесконечное каррирование sum(1)(2)(3)...? (Циан)</b></summary>

Задача-ловушка: заранее неизвестно, сколько будет вызовов, значит по количеству аргументов остановиться нельзя. Решение — всегда возвращать функцию, а результат отдавать в момент, когда движку понадобится примитив.

```js
function sum(a) {
  let total = a;

  function inner(b) {
    total += b;
    return inner;
  }

  inner[Symbol.toPrimitive] = () => total;

  return inner;
}

console.log(+sum(1)(2)(3));     // 6
console.log(sum(1)(2)(3) + 4);  // 10
console.log(`${sum(5)(5)}`);    // '10'
```

Каждый вызов возвращает ту же функцию `inner`, накапливая сумму в замыкании. Когда результат попадает в контекст, требующий примитива — унарный плюс, конкатенация, шаблонная строка, сравнение — срабатывает `Symbol.toPrimitive`.

Вместо `Symbol.toPrimitive` можно определить `valueOf` или `toString`, но тогда поведение будет зависеть от того, какой хинт запросил движок. `Symbol.toPrimitive` перекрывает оба случая и потому надёжнее.

Вариант без приведения типов — остановка по пустому вызову:

```js
function sum(a) {
  return function (b) {
    if (b === undefined) return a;
    return sum(a + b);
  };
}

sum(1)(2)(3)(); // 6
```

Этот вопрос любят, потому что он связывает сразу три темы: замыкания, каррирование и приведение типов. Хорошо, если в ответе прозвучит, что `console.log(sum(1)(2))` без приведения выведет функцию, а не число.

# Композиция функций

<details>
<summary><b>Что такое композиция функций и чем compose отличается от pipe? (Циан)</b></summary>

**Композиция** — объединение нескольких функций в одну так, что результат каждой становится аргументом следующей. Отличаются `compose` и `pipe` только направлением обхода.

- `compose(f, g)(x)` — справа налево, как в математике: `f(g(x))`.

- `pipe(f, g)(x)` — слева направо, в порядке чтения: `g(f(x))`.

```js
const compose = (...fns) => (x) => fns.reduceRight((acc, fn) => fn(acc), x);
const pipe = (...fns) => (x) => fns.reduce((acc, fn) => fn(acc), x);

const inc = (x) => x + 1;
const dbl = (x) => x * 2;

pipe(inc, dbl)(3);     // 8  — сначала 3 + 1 = 4, затем 4 * 2 = 8
compose(inc, dbl)(3);  // 7  — сначала 3 * 2 = 6, затем 6 + 1 = 7
```

Разница между реализациями — ровно один метод: `reduce` против `reduceRight`.

На практике `pipe` читается легче, поэтому его выбирают чаще: последовательность в коде совпадает с последовательностью выполнения. `compose` привычнее тем, кто пришёл из функциональных языков.

**Ограничения, о которых спросят следом:**

- Обе реализации выше передают между функциями ровно одно значение. Чтобы работать с несколькими аргументами, первую функцию делают вариадической: `(...args) => fns.reduce(...)` с отдельным первым вызовом.

- Асинхронные функции так не скомпонуются — на промежуточном шаге в следующую функцию прилетит `Promise`. Для этого нужен отдельный `asyncPipe` на `reduce` с `await`:

```js
const asyncPipe = (...fns) => (x) =>
  fns.reduce((acc, fn) => acc.then(fn), Promise.resolve(x));
```

- Отладка композиции хуже, чем у обычного кода: в стектрейсе видно только `reduce`. Помогает функция-шпион `tap`, которая логирует значение и передаёт его дальше без изменений.

</details>
